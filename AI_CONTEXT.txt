------------------------------------------------------------------------------
1. PROJECT OVERVIEW
------------------------------------------------------------------------------

The MoSim Mod Tracker is a personal progress tracker for making robot mods for
MoSim (an FRC robot simulator built on Unity). It is inspired by LiveSplit (the
speedrunning split timer) — you check off steps as you complete them for each
robot you're modding.

The app is built for ONE person (the repo owner). There is no multi-user
collaboration. The "Claimed" status that existed in the original MoSim community
tracker spreadsheet is intentionally removed — if you haven't started a robot,
it's Planned; once you open Unity, it's In Unity.

The project is meant to be forked / cloned by other MoSim modders who can run
their own instance with their own server.


------------------------------------------------------------------------------
2. WHAT MoSim IS
------------------------------------------------------------------------------

MoSim is an FRC (FIRST Robotics Competition) robot simulator. Modders create
robot mods by:
1. Exporting robot CAD from Onshape/Fusion to GLTF
2. Optimizing the mesh in Blender
3. Setting up the robot prefab in the MoSim Unity project
4. Writing a C# robot script (extends ReefscapeRobotBase)
5. Building with Unity Addressables and publishing the mod

The split template is derived from the official MoSim docs:
https://docs.mosimulator.com/modding/intro
https://docs.mosimulator.com/modding/lynk-walkthrough/ (9496 Lynk robot walkthrough, 9 pages)

There are 10 steps, 53 sub-steps total.

3. TECH STACK
------------------------------------------------------------------------------

Web frontend:
  - React 18 + TypeScript + Vite 5
  - React Router v6 (HashRouter — so it works from file:// and any static host)
  - No CSS framework — hand-written CSS with custom properties (variables) for
    3 themes: dark, light, cloud (soft blue MSI-Center style)
  - No state management library — custom backend abstraction + React Context

Storage backend:
  - HTTPBackend: Express REST API + SQLite (server-side). All data lives on
    your own server. No Firebase, no third-party database.
  - Auth: Google OAuth 2.0 via the server. Web mode uses session cookies;
    Desktop (Tauri) mode uses JWT Bearer tokens stored in localStorage.
  - The Backend interface is still in web/src/store/backend.ts — components
    call useStore() and never import HTTPBackend directly.

Desktop app:
  - Tauri 2.x (Rust + system WebView: WebView2/WKWebView/WebKitGTK)
  - ~50 ms startup, ~5-10 MB installer bundle
  - UI renders from bundled local build (no loading from remote server for UI)
  - Only data fetches go to the server
  - Exposes window.desktop API via web/src/lib/desktop.ts (Tauri invoke bridge)
  - Custom URL scheme mosim:// used for OAuth deep-link callback
  - Cross-platform packaging built into Tauri; GitHub Actions CI builds all
    platforms on version tag push

Server:
  - Node.js + Express (server/server.js, server/api.js)
  - better-sqlite3 for SQLite (server/db.js)
  - google-auth-library for OAuth; jsonwebtoken for session JWTs
  - Deployed on DigitalOcean Ubuntu droplet with nginx + certbot HTTPS
  - Managed by server/manage.sh (setup, deploy, restart, logs, status)

AI features:
  - Two providers: Anthropic Claude API (direct browser fetch with the
    anthropic-dangerous-direct-browser-access header) OR local Ollama
  - Provider, API key, model name all stored in localStorage ONLY — never
    written to the server or any third-party service
  - System prompt in web/src/ai/reference.ts explains MoSim APIs to Claude
  - Script library (Scripts page): drag-drop .cs files in, all fed to AI as
    examples by default, with checkboxes to EXCLUDE (not include)
  - JSONL export for fine-tuning your own model (one training pair per script:
    system + user description + assistant script content)

5. DATA MODEL (types.ts + server DB)
------------------------------------------------------------------------------

RobotStatus = 'planned' | 'in-unity' | 'semi-functional' | 'released'
  NOTE: 'claimed' was removed (single-person tracker, no claiming).
  normalizeRobot() maps old 'claimed' -> 'planned', 'active' -> 'in-unity',
  'complete' -> 'released' for backwards compatibility.

ModType = '' | 'team-made' | 'team-approved' | 'unofficial' | 'official' | 'base-game'

Robot {
  id: string
  name: string             // e.g. "Lynk"
  team: string             // e.g. "9496"
  game: string             // e.g. "Reefscape"
  status: RobotStatus
  modType: ModType
  modpackId: string | null
  repoId: string | null    // links to a Repo
  private: boolean
  notes: string
  order: number            // manual sort order
  createdAt: number        // Unix ms timestamp
  progress: Record<string, StepProgress>  // step id -> StepProgress
}

StepProgress {
  subs: Record<string, boolean>  // sub-step id -> checked
  note: string
}

Modpack {
  id, name, game, description, private, order, createdAt
}

Repo {
  id, name
  localPath: string        // absolute path on this machine (for desktop scanning)
  remoteUrl: string        // GitHub URL (shown as a link)
  private: boolean
  order, createdAt
  scan: RepoScan | null    // cached result of last desktop scan
}

RepoScan {
  scannedAt: number
  robots: ScannedRobot[]
}

ScannedRobot {
  name: string             // folder name (usually team number)
  relPath: string          // path relative to repo root
  lastModified: number     // Unix ms of newest git commit
  scripts: string[]        // repo-relative paths of .cs files inside the folder
}

ScriptDoc {
  id, name                 // filename e.g. "Lynk.cs"
  description: string      // what the robot does; becomes the prompt in JSONL export
  content: string          // raw C# file content
  robotId: string | null   // optionally linked to a tracked robot
  order, createdAt
}

Server-side SQLite schema (db.js):
  All tables store data as SQLite columns with JSON blobs for complex fields
  (progress, scan). The ownerUid column is the Google sub (user ID) from the
  OAuth token. All API routes filter by the authenticated user's UID.

6. SPLIT TEMPLATE (steps.json)
------------------------------------------------------------------------------

10 steps at repo root (shared between web and Tauri desktop):

Step 1: Model Prep (5 sub-steps)
  - Export CAD to GLTF (Team(Year), coarse quality)
  - Swap to simplified swerve modules
  - Import into Blender (merge vertices, delete defaults)
  - Optimize mesh (merge verts, limited dissolve, decimate, weighted normal)
  - Export as FBX

Step 2: Editor Setup (2 sub-steps)
  - Open MoSim Unity project
  - Set external script editor + Unity extension

Step 3: Import & Modpack (6 sub-steps)
  - Create pack folder under Prefabs/<Game>/Robots/Mods
  - Create ModpackMetadata scriptable object
  - Copy example robot folder
  - Rename + fill robot ScriptableObject
  - Import FBX under Imports/<Game>/Models/Robots/<Team>
  - Strip example prefab to drivetrain

Step 4: Hierarchy Setup (6 sub-steps)
  - Rotate upright, match height to wheels
  - Unpack model, create Stationary empty
  - Create empties per mechanism
  - Sort parts into mechanisms
  - Align pivot empties
  - Apply materials/colors

Step 5: Colliders & Physics (5 sub-steps)
  - Box colliders on tubing, compound for odd shapes
  - Separate collider children for game piece interaction
  - Assign physics materials
  - Set layer to Robot (root + all children)
  - Move wheels to match real robot

Step 6: Robot Code (7 sub-steps)
  - Create robot class from RobotBase template
  - Create Setpoint ScriptableObject class
  - Declare elevator/joints + PIDs
  - Target fields + SetSetpoint/UpdateSetpoints helpers
  - Fill setpoint switch
  - Game piece controllers (preload, stow, RequestIntake)
  - PlacePiece / release-with-force logic

Step 7: Editor Components (6 sub-steps)
  - Strip root prefab, add robot script + GenericElevator + GamePiece Controller
  - GenericJoints on stages/arms
  - Configure elevator (stage order, type, PID, height/overlap/carriage)
  - Create setpoint SO assets
  - Intake empties with trigger colliders
  - Set Robot Spawn override; test in play mode

Step 8: Tuning & Refinement (5 sub-steps)
  - Tune setpoint heights/angles
  - Set release forces in PlacePiece
  - Fix collider/intake bugs
  - Add + tune Auto Align
  - Mass tweaks

Step 9: Climber & Polish (5 sub-steps)
  - Climber joints (disable automatic tensor)
  - Climb scorer + trigger box
  - Import team logo, assign it
  - Main-menu display prefab
  - Tutorial cards

Step 10: Build & Ship (6 sub-steps)
  - Addressables group (drag mod folder, add modpack_metadata label)
  - Set custom build/load paths; Include In Build only your mod
  - Build with Default Build Script
  - Collect .bundle + catalog.hash/json + settings.json + mod DLL
  - Drop into Mods folder and test in MoSim
  - Build Win/macOS/Linux, zip, publish, submit for review

7. STORE / BACKEND ABSTRACTION
------------------------------------------------------------------------------

The app talks ONLY to the Backend interface (web/src/store/backend.ts).
Components call `const { robots, api, canEdit } = useStore()` — they never
import HTTPBackend directly.

Backend interface methods:
  init(onChange)         // start subscriptions; calls onChange with Partial<StoreState>
  dispose()              // clean up listeners
  addRobot / updateRobot / deleteRobot
  addModpack / updateModpack / setModpackPrivacy / deleteModpack / setRobotModpack
  addRepo / updateRepo / deleteRepo / saveRepoScan
  addScript / updateScript / deleteScript
  signIn / signOut

StoreState:
  ready: boolean         // false until first load completes
  user: UserInfo | null  // null if not signed in
  robots / modpacks / repos / scripts: arrays, already sorted
  canEdit: boolean       // true if signed in
  error: string | null

HTTPBackend (web/src/store/http.ts):
  - _serverUrl: determined at runtime. In Tauri mode, calls get_server_url Rust
    command (reads mosim.conf). In web mode, empty string (uses relative URLs).
  - _token: JWT Bearer token (Tauri only). Stored in localStorage as 'mosim_token'.
    In web mode, session cookie is used instead (sent automatically by the browser).
  - _req(): builds fetch with appropriate URL + auth header + credentials:include.
    On 401, clears token if in Bearer mode.
  - init(): calls _initAsync(). In Tauri mode, loads serverUrl + token, sets up
    tauriListen for 'mosim:auth-token' events (deep-link OAuth callback).
  - dispose(): clears _disposed flag, calls unlisten to clean up Tauri event listener.
  - signIn(): In Tauri mode, opens ${serverUrl}/api/auth/login?desktop=1 in system
    browser. In web mode, redirects window.location.href to /api/auth/login.
  - signOut(): In Tauri mode, clears localStorage token. In web mode, POST logout.
  - _load(): fetches /api/me to get user + all data arrays.

_disposed flag pattern:
  If dispose() is called before _initAsync() completes (React StrictMode double-
  invoke, hot reload), the unlisten is called immediately and _initAsync returns
  early. This prevents memory leaks from dangling Tauri event listeners.

8. SERVER API (server/api.js)
------------------------------------------------------------------------------

Auth endpoints:
  GET /api/auth/login        Redirects to Google OAuth. ?desktop=1 passes flag
                             through state JWT so callback knows to use deep link.
  GET /api/auth/callback     OAuth callback. If desktop=1 in state: redirects to
                             mosim://auth?token=<jwt>. Else: sets session cookie,
                             redirects to /#/.
  POST /api/auth/logout      Clears session cookie.
  GET /api/me                Returns current user info (null if not authenticated).

Data endpoints (all require authentication):
  /api/robots                CRUD for robots
  /api/modpacks              CRUD for modpacks
  /api/repos                 CRUD for repos + POST /api/repos/:id/scan (save scan)
  /api/scripts               CRUD for scripts

Authentication middleware (requireAuth):
  1. Checks req.cookies.session (web mode — httpOnly cookie set at login)
  2. Falls back to Authorization: Bearer <token> header (Tauri mode)
  3. Verifies JWT with JWT_SECRET; attaches user info to req.user

CORS for Tauri origins:
  Tauri webview origins are 'tauri://localhost' (macOS) and 'http://tauri.localhost'
  (Windows/Linux). The server adds CORS headers for these origins only.

Desktop OAuth flow:
  1. User clicks Sign In in Tauri app
  2. openInBrowser() opens system browser to /api/auth/login?desktop=1
  3. Server embeds desktop:1 in state JWT
  4. After Google auth, server issues JWT and redirects to mosim://auth?token=...
  5. Tauri deep-link plugin catches mosim://auth URL
  6. lib.rs emits 'mosim:auth-token' event with the token string
  7. HTTPBackend listener stores token in localStorage + triggers _load()

Environment variables (server/.env — gitignored, never committed):
  GOOGLE_CLIENT_ID           OAuth 2.0 Client ID from Google Cloud Console
  GOOGLE_CLIENT_SECRET       OAuth 2.0 Client Secret
  OAUTH_REDIRECT_URI         Must match URI registered in Google Console exactly
  JWT_SECRET                 Random 32-byte hex; signs all session tokens.
                             Changing this invalidates all existing sessions.
  NODE_ENV                   'production' (enables secure cookies)
  PORT                       Port for Node server (default 8787)

9. TAURI DESKTOP APP
------------------------------------------------------------------------------

Architecture:
  - src-tauri/src/main.rs: entry point, calls mosim_mod_tracker_lib::run()
  - src-tauri/src/lib.rs: Tauri Builder with plugins + deep-link event handler
  - src-tauri/src/commands.rs: all native Rust commands exposed to JS
  - src-tauri/src/config.rs: get_server_url() reads MOSIM_URL env or mosim.conf

Commands (callable from JS via invoke()):
  get_server_url()           -> String: checks MOSIM_URL env, then mosim.conf
                               next to exe, falls back to http://localhost:8787
  toggle_pin(window)         -> bool: toggles always-on-top, returns new state
  is_pinned(window)          -> bool
  set_expanded(window, bool) -> (): 360x640 compact or 1000x800 expanded
  close_window(window)       -> ()
  open_path(pathOrUrl, app)  -> (): opens URL in system browser or path in explorer
  scan_repo(localPath)       -> ScanResult: walks repo for robot prefab folders
  read_script(repoPath, relPath) -> ScriptResult: reads .cs file content

scan_repo security:
  - Stack-based BFS from localPath
  - Skips dirs: Library, Temp, obj, Logs, node_modules, .git, .idea, UserSettings
  - Finds dirs that contain a .prefab file and have 'Robots' as an ancestor dir
  - Does not descend into robot folders themselves (they're leaf nodes)
  - Last-modified via git -C <repo> log -1 --format=%ct -- <rel_path>
  - Falls back to recursive mtime scan (depth=3) for non-git repos

read_script security:
  - Rejects anything not ending in .cs
  - Rejects paths containing ..
  - Canonicalizes both repo root and full path; checks full path starts_with
    repo root using Rust's Path::starts_with (no path traversal possible)

Deep-link handler (lib.rs):
  Listens for 'deep-link://new-url' event from tauri-plugin-deep-link.
  Parses the URL as mosim://auth?token=<jwt> and re-emits as
  'mosim:auth-token' event (picked up by HTTPBackend in JS).

mosim.conf format (text file next to exe):
  MOSIM_URL=https://mods.yoursite.com

Tauri webview origins:
  macOS:         tauri://localhost
  Windows/Linux: http://tauri.localhost
  (Server CORS whitelist includes both)

JS bridge (web/src/lib/desktop.ts):
  isTauri() checks '__TAURI_INTERNALS__' in window.
  When Tauri is detected, sets up window.desktop = { ... } with camelCase
  wrappers that call Rust commands via invoke().
  Note: Tauri 2 auto-maps snake_case Rust params to camelCase in JS.
  (E.g. Rust read_script(repo_path, rel_path) -> JS invoke('read_script',
  { repoPath, relPath }))

Installer/config:
  Windows:  Inno Setup NSIS .exe. Installer wizard asks for server URL on
            first install; writes mosim.conf next to the exe.
  macOS:    .dmg created by create-dmg with background image and .icns icon.
            mosim.conf lives at /Applications/mosim.conf or beside the .app.
  Linux:    .AppImage (self-contained). mosim.conf next to AppImage.
            AppRun script writes default mosim.conf on first launch.

Building:
  npm run dev    -> starts Tauri dev window + Vite HMR together
  npm run build  -> production Tauri installer for current platform

11. PAGE DESCRIPTIONS
------------------------------------------------------------------------------

RobotsPage (/):
  - Spreadsheet-style table of robots with status 'in-unity', 'semi-functional',
    or 'released' (not 'planned')
  - Columns: Team | Robot | Status | Mod Type | Pack | Repo | Progress | Notes
  - Filter chips: All / In Unity / Semi-Functional / Released
  - "In Unity" rows show the current step name in a sub-row
  - Click row -> navigate to /robot/:id
  - RobotForm at top to add a new robot (default status: 'in-unity')

PlannedPage (/planned):
  - List of robots with status='planned'
  - Shows name, team, game, notes textarea
  - "Start modding →" button sets status to 'in-unity' and navigates to detail
  - Can toggle private flag per robot
  - RobotForm to add planned robots

RobotDetailPage (/robot/:id):
  - Two-column layout: splits (left) + sidebar (right, sticky)
  - Sidebar: "What's left" (remaining steps list) + robot notes textarea
  - Status pill selector + mod type pill selector + modpack selector + repo selector
  - Inline-editable name, team, game fields
  - Split steps list (Splits component)
  - AI Script Generator panel (AiScriptPanel, collapsible) at bottom
  - Delete robot button

ModpacksPage (/modpacks):
  - List of modpacks with their member robots shown as chips
  - Inline name/game/description editing
  - Private toggle
  - Add/delete modpack
  - Robot membership managed via setRobotModpack on the robot detail page

ReposPage (/repos):
  - List of repos with name, local path, remote URL
  - "Scan" button triggers window.desktop.scanRepo() (desktop only)
  - Shows a table of robots found in the scan (name, last modified, script count)
  - Scan results are cached on the Repo record (scan field)

ScriptsPage (/scripts):
  - Drag-and-drop zone for .cs files (also click-to-browse)
  - Accepts .cs and .txt, max 400 KB per file
  - Script rows: expandable, shows description textarea + robot link + delete
  - Description is the "prompt" for JSONL training data export
  - "Export training dataset (JSONL)" button at top when scripts exist
  - JSONL format: one JSON object per line, messages: [system, user, assistant]
  - Warning count if scripts are missing descriptions before export

CompactPage (/compact):
  - LiveSplit-style compact overlay (no Shell/nav)
  - Robot selector dropdown at top

14. CI / RELEASE PIPELINE
------------------------------------------------------------------------------

.github/workflows/release.yml triggers on version tags: git tag v1.2.3 && git push --tags

Matrix jobs (run in parallel):
  - windows-latest         -> NSIS .exe
  - macos-latest (aarch64) -> .dmg (Apple Silicon)
  - macos-latest (x86_64)  -> .dmg (Intel)
  - ubuntu-22.04           -> .AppImage

Steps in each job:
  1. actions/checkout
  2. Python 3.11 + pip install pillow + python installer/generate-assets.py
  3. Node.js 20 + npm cache
  4. dtolnay/rust-toolchain@stable (macOS jobs add both aarch64 + x86_64 targets)
  5. Swatinem/rust-cache (workspaces: src-tauri)
  6. Linux only: apt install libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev patchelf
  7. npm ci (root) + npm --prefix web ci
  8. npm run tauri -- icon installer/assets/icon.png
  9. tauri-apps/tauri-action@v0 with GITHUB_TOKEN
     Creates GitHub Release, attaches all platform installers

To release a new version:
  1. Update version in src-tauri/tauri.conf.json and src-tauri/Cargo.toml
  2. Commit and push
  3. git tag v1.2.3 && git push --tags
  GitHub Actions builds all four platform artifacts (~15 min).

17. KEY CODE PATTERNS TO FOLLOW
------------------------------------------------------------------------------

Tauri command naming:
  - Rust functions: snake_case (e.g. scan_repo, read_script)
  - Tauri 2 serde default auto-maps to camelCase in JS
  - JS invoke calls: invoke('scan_repo', { localPath }) (camelCase args)
  - Struct fields with #[serde(rename_all = "camelCase")] map correctly

isTauri() gating:
  - Always check isTauri() before using any Tauri-specific API
  - window.desktop is undefined in a browser
  - Dynamic imports: await import('@tauri-apps/api/core') to avoid bundling
    in web mode (tree-shaking doesn't work on static top-level imports of
    Tauri APIs since the module fails to load outside of Tauri)

State mutations:
  - ALWAYS go through the Backend interface (api.updateRobot etc.)
  - NEVER mutate arrays or objects from useStore() directly
  - The store is read-only from the component side

Adding a new page:
  1. Create web/src/pages/NewPage.tsx
  2. Add import + <NavLink> in App.tsx nav
  3. Add <Route path="/new-page" element={<NewPage />} /> in App.tsx routes
  4. Add CSS in styles.css with a section comment

Adding a new data type:
  1. Add interface + New* type to types.ts
  2. Add to StoreState in backend.ts
  3. Add add*/update*/delete* methods to Backend interface
  4. Add server routes in server/api.js
  5. Add SQLite table + helpers in server/db.js
  6. Implement backend methods in http.ts

Security — API key handling:
  - The API key is the user's own key, stored ONLY in this device's localStorage
  - NEVER write to the server DB, NEVER send to any server except api.anthropic.com
  - JWT_SECRET is server-side only and never exposed to the frontend
  - read_script validates .cs extension + canonicalize path traversal check

18. HOW TO RUN
------------------------------------------------------------------------------

Web (browser only — no desktop features):
  # Terminal 1 — server
  cd server
  npm install          (first time)
  cp .env.example .env # fill in Google OAuth credentials + JWT_SECRET
  node server.js

  # Terminal 2 — frontend
  cd web
  npm install          (first time)
  npm run dev          -> http://localhost:5173
                         (proxies /api/* to localhost:8787)

Tauri desktop app (development):
  # Prerequisites: Rust (rustup.rs), Node.js 20, WebView2 (Windows)
  npm install               (root — installs @tauri-apps/cli)
  npm --prefix web install  (web — installs React + @tauri-apps/api)

  # In a separate terminal, start the server first:
  node server/server.js

  # Then start Tauri dev (opens desktop window + Vite HMR):
  npm run dev

  # On first launch without mosim.conf, defaults to http://localhost:8787.
  # To point at a remote server, create src-tauri/mosim.conf:
  #   MOSIM_URL=https://mods.yoursite.com

Tauri desktop app (production build):
  npm run build
  # Windows → src-tauri/target/release/bundle/nsis/*.exe
  # macOS   → src-tauri/target/release/bundle/dmg/*.dmg
  # Linux   → src-tauri/target/release/bundle/appimage/*.AppImage

Server deployment:
  See docs/server-setup.md for the full guide.
  Quick summary: DigitalOcean Ubuntu droplet, fill in server/manage.sh variables,
  run `sudo bash manage.sh setup` on the droplet. Subsequent deploys:
  `sudo bash manage.sh deploy`
