------------------------------------------------------------------------------
1. PROJECT OVERVIEW
------------------------------------------------------------------------------

The MoSim Mod Tracker is a personal progress tracker for making robot mods for
MoSim (an FRC robot simulator built on Unity). It is inspired by LiveSplit (the
speedrunning split timer) — you check off steps as you complete them for each
robot you're modding.

The app is built for ONE person (the repo owner). There is no multi-user
collaboration. The "Claimed" status that existed in the original MoSim community
tracker spreadsheet is intentionally removed — if you haven't started a robot,
it's Planned; once you open Unity, it's In Unity.

The project is meant to be forked / cloned by other MoSim modders who can run
their own instance with their own Firebase project (or just use local mode, no
account needed).


------------------------------------------------------------------------------
2. WHAT MoSim IS
------------------------------------------------------------------------------

MoSim is an FRC (FIRST Robotics Competition) robot simulator. Modders create
robot mods by:
1. Exporting robot CAD from Onshape/Fusion to GLTF
2. Optimizing the mesh in Blender
3. Setting up the robot prefab in the MoSim Unity project
4. Writing a C# robot script (extends ReefscapeRobotBase)
5. Building with Unity Addressables and publishing the mod

The split template is derived from the official MoSim docs:
https://docs.mosimulator.com/modding/intro
https://docs.mosimulator.com/modding/lynk-walkthrough/ (9496 Lynk robot walkthrough, 9 pages)

There are 10 steps, 53 sub-steps total.

3. TECH STACK
------------------------------------------------------------------------------

Web frontend:
  - React 18 + TypeScript + Vite 5
  - React Router v6 (HashRouter — so it works from file:// and any static host)
  - No CSS framework — hand-written CSS with custom properties (variables) for
    3 themes: dark, light, cloud (soft blue MSI-Center style)
  - No state management library — custom backend abstraction + React Context

Storage backends (same TypeScript interface, swapped at runtime):
  - LocalBackend: localStorage JSON blob, no account needed, syncs between
    tabs via the 'storage' event
  - CloudBackend: Firebase Firestore (real-time onSnapshot subscriptions) +
    Firebase Auth (Google sign-in popup)
  - Which one is used: if firebaseConfig in firebase-config.ts is non-null,
    CloudBackend is used; otherwise LocalBackend

Desktop app:
  - Python (3.8+) + pywebview (pip install pywebview)
  - Serves web/dist/ on a random localhost port via Python's built-in HTTPServer
  - Opens a native OS window (WebView2 on Windows, WKWebView on macOS, GTK on Linux)
  - Exposes a JS API (window.desktop.*) via a shim over window.pywebview.api.*
  - No Electron, no Node.js required to run the desktop app

AI features:
  - Two providers: Anthropic Claude API (direct browser fetch with the
    anthropic-dangerous-direct-browser-access header) OR local Ollama
  - Provider, API key, model name all stored in localStorage only — never
    written to Firestore or any server
  - System prompt in web/src/ai/reference.ts explains MoSim APIs to Claude
  - Script library (Scripts page): drag-drop .cs files in, all fed to AI as
    examples by default, with checkboxes to EXCLUDE (not include)
  - JSONL export for fine-tuning your own model (one training pair per script:
    system + user description + assistant script content)

Server/hosting:
  - server/: Express static server + DEPLOY.md for a DigitalOcean droplet
  - Firebase Hosting also works (firebase deploy --only hosting)
  - Firebase stores all data; the static server is just a file host

5. DATA MODEL (types.ts)
------------------------------------------------------------------------------

RobotStatus = 'planned' | 'in-unity' | 'semi-functional' | 'released'
  NOTE: 'claimed' was removed (single-person tracker, no claiming).
  normalizeRobot() maps old 'claimed' -> 'planned', 'active' -> 'in-unity',
  'complete' -> 'released' for backwards compatibility.

ModType = '' | 'team-made' | 'team-approved' | 'unofficial' | 'official' | 'base-game'

Robot {
  id: string
  name: string             // e.g. "Lynk"
  team: string             // e.g. "9496"
  game: string             // e.g. "Reefscape"
  status: RobotStatus
  modType: ModType
  modpackId: string | null
  repoId: string | null    // links to a Repo
  private: boolean
  modpackPrivate: boolean  // DENORMALIZED copy of parent modpack's private flag
                           // (Firestore can't join in security rules, so this
                           // flag is copied to each robot doc)
  ownerUid: string | null
  notes: string
  order: number            // manual sort order
  createdAt: number        // Date.now() Unix ms
  progress: Record<string, StepProgress>  // step id -> StepProgress
}

StepProgress {
  subs: Record<string, boolean>  // sub-step id -> checked
  note: string
}

Modpack {
  id, name, game, description, private, ownerUid, order, createdAt
}

Repo {
  id, name
  localPath: string        // absolute path on this machine (for desktop scanning)
  remoteUrl: string        // GitHub URL (shown as a link)
  private: boolean
  ownerUid, order, createdAt
  scan: RepoScan | null    // cached result of last desktop scan
}

RepoScan {
  scannedAt: number
  robots: ScannedRobot[]
}

ScannedRobot {
  name: string             // folder name (usually team number)
  relPath: string          // path relative to repo root
  lastModified: number     // Unix ms of newest git commit
  scripts: string[]        // repo-relative paths of .cs files inside the folder
}

ScriptDoc {
  id, name                 // filename e.g. "Lynk.cs"
  description: string      // what the robot does; becomes the prompt in JSONL export
  content: string          // raw C# file content
  robotId: string | null   // optionally linked to a tracked robot
  ownerUid, order, createdAt
}

New* types = Omit<Full, 'id' | 'ownerUid' | 'order' | 'createdAt' | ...>
  These are what callers provide; the backend fills in the rest.

6. SPLIT TEMPLATE (steps.json)
------------------------------------------------------------------------------

10 steps at repo root (shared between web and Python desktop):

Step 1: Model Prep (5 sub-steps)
  - Export CAD to GLTF (Team(Year), coarse quality)
  - Swap to simplified swerve modules
  - Import into Blender (merge vertices, delete defaults)
  - Optimize mesh (merge verts, limited dissolve, decimate, weighted normal)
  - Export as FBX

Step 2: Editor Setup (2 sub-steps)
  - Open MoSim Unity project
  - Set external script editor + Unity extension

Step 3: Import & Modpack (6 sub-steps)
  - Create pack folder under Prefabs/<Game>/Robots/Mods
  - Create ModpackMetadata scriptable object
  - Copy example robot folder
  - Rename + fill robot ScriptableObject
  - Import FBX under Imports/<Game>/Models/Robots/<Team>
  - Strip example prefab to drivetrain

Step 4: Hierarchy Setup (6 sub-steps)
  - Rotate upright, match height to wheels
  - Unpack model, create Stationary empty
  - Create empties per mechanism
  - Sort parts into mechanisms
  - Align pivot empties
  - Apply materials/colors

Step 5: Colliders & Physics (5 sub-steps)
  - Box colliders on tubing, compound for odd shapes
  - Separate collider children for game piece interaction
  - Assign physics materials
  - Set layer to Robot (root + all children)
  - Move wheels to match real robot

Step 6: Robot Code (7 sub-steps)
  - Create robot class from RobotBase template
  - Create Setpoint ScriptableObject class
  - Declare elevator/joints + PIDs
  - Target fields + SetSetpoint/UpdateSetpoints helpers
  - Fill setpoint switch
  - Game piece controllers (preload, stow, RequestIntake)
  - PlacePiece / release-with-force logic

Step 7: Editor Components (6 sub-steps)
  - Strip root prefab, add robot script + GenericElevator + GamePiece Controller
  - GenericJoints on stages/arms
  - Configure elevator (stage order, type, PID, height/overlap/carriage)
  - Create setpoint SO assets
  - Intake empties with trigger colliders
  - Set Robot Spawn override; test in play mode

Step 8: Tuning & Refinement (5 sub-steps)
  - Tune setpoint heights/angles
  - Set release forces in PlacePiece
  - Fix collider/intake bugs
  - Add + tune Auto Align
  - Mass tweaks

Step 9: Climber & Polish (5 sub-steps)
  - Climber joints (disable automatic tensor)
  - Climb scorer + trigger box
  - Import team logo, assign it
  - Main-menu display prefab
  - Tutorial cards

Step 10: Build & Ship (6 sub-steps)
  - Addressables group (drag mod folder, add modpack_metadata label)
  - Set custom build/load paths; Include In Build only your mod
  - Build with Default Build Script
  - Collect .bundle + catalog.hash/json + settings.json + mod DLL
  - Drop into Mods folder and test in MoSim
  - Build Win/macOS/Linux, zip, publish, submit for review

7. STORE / BACKEND ABSTRACTION
------------------------------------------------------------------------------

The app talks ONLY to the Backend interface (web/src/store/backend.ts).
Components call `const { robots, api, canEdit } = useStore()` — they never
import LocalBackend or CloudBackend directly.

Backend interface methods:
  init(onChange)         // start subscriptions; calls onChange with Partial<StoreState>
  dispose()              // clean up listeners
  addRobot / updateRobot / deleteRobot
  addModpack / updateModpack / setModpackPrivacy / deleteModpack / setRobotModpack
  addRepo / updateRepo / deleteRepo / saveRepoScan
  addScript / updateScript / deleteScript
  signIn / signOut

StoreState:
  mode: 'local' | 'cloud'
  ready: boolean         // false until first load completes
  user: UserInfo | null  // null if not signed in or in local mode
  robots / modpacks / repos / scripts: arrays, already sorted
  canEdit: boolean       // true in local mode or if signed in
  error: string | null

Selection logic in StoreContext.tsx:
  firebaseConfig !== null  =>  CloudBackend
  firebaseConfig === null  =>  LocalBackend (DEFAULT — works with zero setup)

LocalBackend details:
  - localStorage key: 'mosim-mod-tracker'
  - Syncs between tabs via the 'storage' window event
  - normalizeRobot() applied on every read (handles old status values)

CloudBackend details:
  - Two Firestore queries per collection: public (private==false) + owner (ownerUid==uid)
  - Results merged by document ID into sorted arrays
  - onSnapshot subscriptions = live updates across devices
  - ready=true only after every active query has responded at least once
  - Scripts are NEVER queried publicly (only owner query)
  - Firestore security rules in firestore.rules enforce read/write access server-side

8. FIRESTORE RULES SUMMARY
------------------------------------------------------------------------------

Collections: robots, modpacks, repos, scripts

robots:
  read: if (private==false && modpackPrivate==false) OR owner
  create: if signedIn && ownerUid == me
  update/delete: if owner

modpacks:
  read: if private==false OR owner
  create: if signedIn && ownerUid == me
  update/delete: if owner

repos:
  read: if private==false OR owner
  create: if signedIn && ownerUid == me
  update/delete: if owner

scripts:
  read/write: if owner (NEVER public)
  create: if signedIn && ownerUid == me

The rules include a comment explaining how to lock to a single Google UID
(replace signedIn() with request.auth.uid == 'YOUR_UID_HERE' in create rules).

NOTE: modpackPrivate is a denormalized copy of the parent modpack's private flag,
copied to each robot document because Firestore rules can't do cross-collection
lookups. When a modpack's privacy changes, setModpackPrivacy() updates the flag
on all member robots in a batch write.

12. PYTHON DESKTOP APP (app/main.py)
------------------------------------------------------------------------------

Architecture:
  1. Scans for web/dist/ (error if missing — build web/ first)
  2. Starts Python's built-in HTTPServer on a random port, serving web/dist/
  3. Creates a pywebview window (360×640, on_top=True) pointing to
     http://127.0.0.1:{port}/#/compact
  4. DesktopAPI class is passed as js_api to create_window
     -> exposed as window.pywebview.api.method_name() in the page
  5. Injects DESKTOP_SHIM JS every time the page loads, which creates
     window.desktop = { camelCase wrappers around pywebview.api.snake_case }
     This lets the existing React code call window.desktop.scanRepo() etc.
     without knowing it's talking to Python instead of Electron

DesktopAPI methods (Python snake_case -> JS camelCase via shim):
  toggle_pin()     -> togglePin()    Returns bool (new pinned state)
  is_pinned()      -> isPinned()     Returns bool
  set_expanded(b)  -> setExpanded()  360×640 (compact) or 1000×800 (expanded)
  close()          -> close()        Destroys the window
  scan_repo(path)  -> scanRepo()     Returns {ok, error?, robots: ScannedRobot[]}
  read_script(r,p) -> readScript()   Returns {ok, error?, content}
  open_path(s)     -> openPath()     Opens URL in browser or folder in explorer

Always-on-top toggling:
  Windows: ctypes.windll.user32.SetWindowPos() with HWND_TOPMOST/-1 or
           HWND_NOTOPMOST/-2, SWP_NOMOVE|SWP_NOSIZE flags
  macOS:   objc runtime call to NSWindow.setLevel_ (3=floating, 0=normal)
  Linux:   Not supported (pywebview doesn't expose a reliable post-creation
           hook; window starts on_top=True and can't be toggled)

Repo scanning (_scan_robots):
  - Walks Assets/**/Robots/** for folders containing a .prefab file directly
  - Skips folders named 'Robots' or 'Mods' (they're containers, not robot folders)
  - Must have a 'Robots' ancestor in the path
  - Gets last git commit timestamp via: git -C {repo} log -1 --format=%ct -- {rel}
  - Falls back to max file mtime if git is unavailable
  - Returns list sorted by folder name (case-insensitive)
  - Results are stored on the Repo record via api.saveRepoScan()

Security in read_script:
  - Rejects anything not ending in .cs
  - Resolves to absolute path and calls relative_to(repo_root) — raises ValueError
    if the resolved path is outside the repo (path traversal protection)

Pywebview JS API notes:
  - Methods must be on a class passed as js_api=
  - They are called async from JS (return a Promise)
  - Return values must be JSON-serializable (dict, list, str, int, bool)
  - The page must wait for window.pywebview.api to be populated before calling;
    the DESKTOP_SHIM is injected in the window.events.loaded handler which fires
    after pywebview has set up the api object

Dependencies:
  pip install pywebview
  That's it. No other third-party packages.
  Python stdlib used: os, sys, subprocess, threading, webbrowser, http.server,
                      pathlib, ctypes (Windows/macOS only)

  - In the old Electron app it was populated by preload.js contextBridge

19. HOW TO RUN
------------------------------------------------------------------------------

Web (browser):
  cd web
  npm install        (first time only)
  npm run dev        -> http://localhost:5173
  -- or --
  npm run build      -> web/dist/ (static files for production)

Desktop (Python):
  cd {repo root}
  pip install pywebview    (first time only — requires Python 3.8+)
  npm run build            (in web/ — Python app serves web/dist/)
  python app/main.py
  -- or double-click app/run.bat (Windows) / app/run.sh (Mac/Linux)

Firebase setup (to enable cloud sync):
  1. Create project at console.firebase.google.com
  2. Enable Authentication -> Google
  3. Create Firestore database (production mode)
  4. Register a Web app, copy the config object
  5. Paste config into web/src/firebase-config.ts (replace the null)
  6. npm install -g firebase-tools
     firebase login
     firebase use <project-id>
     firebase deploy --only firestore    (deploys rules + indexes)
  7. npm run build (in web/)

DigitalOcean deploy:
  See server/DEPLOY.md for full instructions.
  Summary: scp web/dist/ + server/ to droplet, npm install in server/,
  systemd service, nginx reverse proxy, certbot HTTPS
